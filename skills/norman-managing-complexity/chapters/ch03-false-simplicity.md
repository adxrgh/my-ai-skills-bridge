# 第 3 章：简单的东西如何使生活更复杂

## 核心思想

局部简化常把复杂性推给其他时间、角色或渠道，使完整旅程更困难。

## 本章框架

- **False Simplicity / 虚假简单**：删去可见控件却把负担转移到记忆、模式、步骤或支持渠道。
  - 何时使用：当某个团队宣布步骤减少，但投诉、等待或人工处理增加时。
  - 如何使用：沿端到端旅程绘制复杂性转移：谁在何时承担记忆、协调、异常和恢复。
  - 失效方式：只优化自己的屏幕或部门指标。
- **Service System / 服务系统**：由人、渠道、规则、后台流程与触点共同完成结果的整体。
  - 何时使用：当“简单的东西如何使生活更复杂”相关决策存在多个看似合理的选项时。
  - 如何使用：先标出用户目标与约束，再用“Service System / 服务系统”逐项检查方案；无法观察或验证的判断不算完成。
  - 失效方式：把术语当标签，却没有改变产品行为或验证方法。
- **Journey / 旅程**：用户跨时间和触点完成目标的连续经历，而不是单个屏幕。
  - 何时使用：当“简单的东西如何使生活更复杂”相关决策存在多个看似合理的选项时。
  - 如何使用：先标出用户目标与约束，再用“Journey / 旅程”逐项检查方案；无法观察或验证的判断不算完成。
  - 失效方式：把术语当标签，却没有改变产品行为或验证方法。

## 关键概念

- **False Simplicity / 虚假简单**：删去可见控件却把负担转移到记忆、模式、步骤或支持渠道。
- **Service System / 服务系统**：由人、渠道、规则、后台流程与触点共同完成结果的整体。
- **Journey / 旅程**：用户跨时间和触点完成目标的连续经历，而不是单个屏幕。

## 心智模型

- 把本章看成一个决策过滤器：沿端到端旅程绘制复杂性转移：谁在何时承担记忆、协调、异常和恢复。
- 当局部界面“看起来合理”却让人迟疑时，回到用户目标、情境和反馈链，而不是继续装饰表面。
- 设计主张必须能被研究证据、行为结果或可用性观察推翻；不能被推翻的主张只是偏好。

## 反模式

- **局部最优**：只优化自己的屏幕或部门指标。
- **术语替代证据**：引用框架名称却没有说明用户、任务、约束和验证信号，会让团队产生虚假的确定性。

## Worked Example

自助值机界面少一步，却把异常旅客赶到人工队列；应同时设计正常流、例外识别和顺畅转交。

把例子重新应用到自己的产品时，保留同样的推理顺序：先写目标与情境，再写设计动作，最后写可观察的成功/失败信号。

## 关键结论

1. 沿端到端旅程绘制复杂性转移：谁在何时承担记忆、协调、异常和恢复。
2. 把“False Simplicity / 虚假简单”落实为可观察的界面或流程行为，而不是停留在口号。
3. 用真实情境检查“Journey / 旅程”，并记录失败条件。
