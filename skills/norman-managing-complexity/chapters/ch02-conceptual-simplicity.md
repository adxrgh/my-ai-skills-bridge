# 第 2 章：简单只存在于头脑中

## 核心思想

简单是一种理解状态，不是对象的绝对属性；熟悉的复杂系统可以感觉简单。

## 本章框架

- **Conceptual Simplicity / 概念简单**：用少数稳定规则和清晰模型组织复杂能力，使人能够预测。
  - 何时使用：当团队用视觉极简推断认知简单时。
  - 如何使用：测试用户能否形成稳定预测，而不仅是首次看到的整洁程度。
  - 失效方式：把控件隐藏进模式和菜单，造成记忆与恢复成本。
- **False Simplicity / 虚假简单**：删去可见控件却把负担转移到记忆、模式、步骤或支持渠道。
  - 何时使用：当“简单只存在于头脑中”相关决策存在多个看似合理的选项时。
  - 如何使用：先标出用户目标与约束，再用“False Simplicity / 虚假简单”逐项检查方案；无法观察或验证的判断不算完成。
  - 失效方式：把术语当标签，却没有改变产品行为或验证方法。
- **Coping / 应对机制**：人在复杂系统中借助惯例、外部记忆、分工和近似规则维持行动。
  - 何时使用：当“简单只存在于头脑中”相关决策存在多个看似合理的选项时。
  - 如何使用：先标出用户目标与约束，再用“Coping / 应对机制”逐项检查方案；无法观察或验证的判断不算完成。
  - 失效方式：把术语当标签，却没有改变产品行为或验证方法。

## 关键概念

- **Conceptual Simplicity / 概念简单**：用少数稳定规则和清晰模型组织复杂能力，使人能够预测。
- **False Simplicity / 虚假简单**：删去可见控件却把负担转移到记忆、模式、步骤或支持渠道。
- **Coping / 应对机制**：人在复杂系统中借助惯例、外部记忆、分工和近似规则维持行动。

## 心智模型

- 把本章看成一个决策过滤器：测试用户能否形成稳定预测，而不仅是首次看到的整洁程度。
- 当局部界面“看起来合理”却让人迟疑时，回到用户目标、情境和反馈链，而不是继续装饰表面。
- 设计主张必须能被研究证据、行为结果或可用性观察推翻；不能被推翻的主张只是偏好。

## 反模式

- **表面极简**：把控件隐藏进模式和菜单，造成记忆与恢复成本。
- **术语替代证据**：引用框架名称却没有说明用户、任务、约束和验证信号，会让团队产生虚假的确定性。

## Worked Example

常用厨房中工具很多，但位置稳定、按任务组织后操作自然；酒店厨房即使器具更少，也因陌生映射而更难用。

把例子重新应用到自己的产品时，保留同样的推理顺序：先写目标与情境，再写设计动作，最后写可观察的成功/失败信号。

## 关键结论

1. 测试用户能否形成稳定预测，而不仅是首次看到的整洁程度。
2. 把“Conceptual Simplicity / 概念简单”落实为可观察的界面或流程行为，而不是停留在口号。
3. 用真实情境检查“Coping / 应对机制”，并记录失败条件。
