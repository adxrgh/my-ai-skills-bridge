# 第 1 章：设计复杂生活：为什么复杂是必需的

## 核心思想

有意义的生活和强大工具必然包含复杂性；设计任务是组织复杂性，而非追求最少部件。

## 本章框架

- **Necessary Complexity / 必要复杂性**：复杂任务本身具有不可消除的结构；目标是使其可理解和可管理，而不是假装不存在。
  - 何时使用：当“更简单”成为没有目标和代价说明的需求时。
  - 如何使用：先分离任务固有复杂性与设计制造的费解感，再决定哪些结构必须保留、哪些负担可以转移。
  - 失效方式：把功能数量直接当作复杂度指标，忽略关系和概念模型。
- **Complicatedness / 费解感**：人面对结构、控制或解释混乱时产生的主观困难；它不同于客观复杂性。
  - 何时使用：当“设计复杂生活：为什么复杂是必需的”相关决策存在多个看似合理的选项时。
  - 如何使用：先标出用户目标与约束，再用“Complicatedness / 费解感”逐项检查方案；无法观察或验证的判断不算完成。
  - 失效方式：把术语当标签，却没有改变产品行为或验证方法。
- **Conceptual Simplicity / 概念简单**：用少数稳定规则和清晰模型组织复杂能力，使人能够预测。
  - 何时使用：当“设计复杂生活：为什么复杂是必需的”相关决策存在多个看似合理的选项时。
  - 如何使用：先标出用户目标与约束，再用“Conceptual Simplicity / 概念简单”逐项检查方案；无法观察或验证的判断不算完成。
  - 失效方式：把术语当标签，却没有改变产品行为或验证方法。

## 关键概念

- **Necessary Complexity / 必要复杂性**：复杂任务本身具有不可消除的结构；目标是使其可理解和可管理，而不是假装不存在。
- **Complicatedness / 费解感**：人面对结构、控制或解释混乱时产生的主观困难；它不同于客观复杂性。
- **Conceptual Simplicity / 概念简单**：用少数稳定规则和清晰模型组织复杂能力，使人能够预测。

## 心智模型

- 把本章看成一个决策过滤器：先分离任务固有复杂性与设计制造的费解感，再决定哪些结构必须保留、哪些负担可以转移。
- 当局部界面“看起来合理”却让人迟疑时，回到用户目标、情境和反馈链，而不是继续装饰表面。
- 设计主张必须能被研究证据、行为结果或可用性观察推翻；不能被推翻的主张只是偏好。

## 反模式

- **以删减代替理解**：把功能数量直接当作复杂度指标，忽略关系和概念模型。
- **术语替代证据**：引用框架名称却没有说明用户、任务、约束和验证信号，会让团队产生虚假的确定性。

## Worked Example

专业相机控件很多，但按拍摄意图分组并保持稳定映射后，比只有一个按钮却依赖深层菜单更容易掌握。

把例子重新应用到自己的产品时，保留同样的推理顺序：先写目标与情境，再写设计动作，最后写可观察的成功/失败信号。

## 关键结论

1. 先分离任务固有复杂性与设计制造的费解感，再决定哪些结构必须保留、哪些负担可以转移。
2. 把“Necessary Complexity / 必要复杂性”落实为可观察的界面或流程行为，而不是停留在口号。
3. 用真实情境检查“Conceptual Simplicity / 概念简单”，并记录失败条件。
