# 第 6 章：系统和服务

## 核心思想

体验由整个服务生态交付，单个触点优秀不能补偿后台和跨渠道断裂。

## 本章框架

- **Service System / 服务系统**：由人、渠道、规则、后台流程与触点共同完成结果的整体。
  - 何时使用：当问题跨 App、客服、物流、门店或政策边界时。
  - 如何使用：画出前台触点、后台流程、责任和信息交接，围绕用户结果而非部门组织改造。
  - 失效方式：只重做界面，不改变造成失败的规则与交接。
- **Journey / 旅程**：用户跨时间和触点完成目标的连续经历，而不是单个屏幕。
  - 何时使用：当“系统和服务”相关决策存在多个看似合理的选项时。
  - 如何使用：先标出用户目标与约束，再用“Journey / 旅程”逐项检查方案；无法观察或验证的判断不算完成。
  - 失效方式：把术语当标签，却没有改变产品行为或验证方法。
- **Partnership / 人机伙伴关系**：人负责目标、价值与例外判断，系统负责计算、记忆和稳定执行的互补分工。
  - 何时使用：当“系统和服务”相关决策存在多个看似合理的选项时。
  - 如何使用：先标出用户目标与约束，再用“Partnership / 人机伙伴关系”逐项检查方案；无法观察或验证的判断不算完成。
  - 失效方式：把术语当标签，却没有改变产品行为或验证方法。

## 关键概念

- **Service System / 服务系统**：由人、渠道、规则、后台流程与触点共同完成结果的整体。
- **Journey / 旅程**：用户跨时间和触点完成目标的连续经历，而不是单个屏幕。
- **Partnership / 人机伙伴关系**：人负责目标、价值与例外判断，系统负责计算、记忆和稳定执行的互补分工。

## 心智模型

- 把本章看成一个决策过滤器：画出前台触点、后台流程、责任和信息交接，围绕用户结果而非部门组织改造。
- 当局部界面“看起来合理”却让人迟疑时，回到用户目标、情境和反馈链，而不是继续装饰表面。
- 设计主张必须能被研究证据、行为结果或可用性观察推翻；不能被推翻的主张只是偏好。

## 反模式

- **界面粉饰**：只重做界面，不改变造成失败的规则与交接。
- **术语替代证据**：引用框架名称却没有说明用户、任务、约束和验证信号，会让团队产生虚假的确定性。

## Worked Example

退货流程的关键不是按钮颜色，而是订单识别、资格解释、取件、退款状态和异常客服共享同一事实。

把例子重新应用到自己的产品时，保留同样的推理顺序：先写目标与情境，再写设计动作，最后写可观察的成功/失败信号。

## 关键结论

1. 画出前台触点、后台流程、责任和信息交接，围绕用户结果而非部门组织改造。
2. 把“Service System / 服务系统”落实为可观察的界面或流程行为，而不是停留在口号。
3. 用真实情境检查“Partnership / 人机伙伴关系”，并记录失败条件。
