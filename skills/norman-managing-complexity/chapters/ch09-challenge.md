# 第 9 章：挑战

## 核心思想

复杂性管理是社会技术问题，权力、激励、标准和文化会决定设计是否真正奏效。

## 本章框架

- **Challenge / 挑战**：在效率、透明度、安全、文化和组织利益冲突下持续管理复杂性。
  - 何时使用：当明确的界面修复在组织内反复失败时。
  - 如何使用：把政策、所有权、激励和跨团队依赖纳入问题模型，设置端到端结果指标。
  - 失效方式：把组织性失败留给用户用耐心和记忆补偿。
- **Service System / 服务系统**：由人、渠道、规则、后台流程与触点共同完成结果的整体。
  - 何时使用：当“挑战”相关决策存在多个看似合理的选项时。
  - 如何使用：先标出用户目标与约束，再用“Service System / 服务系统”逐项检查方案；无法观察或验证的判断不算完成。
  - 失效方式：把术语当标签，却没有改变产品行为或验证方法。
- **Necessary Complexity / 必要复杂性**：复杂任务本身具有不可消除的结构；目标是使其可理解和可管理，而不是假装不存在。
  - 何时使用：当“挑战”相关决策存在多个看似合理的选项时。
  - 如何使用：先标出用户目标与约束，再用“Necessary Complexity / 必要复杂性”逐项检查方案；无法观察或验证的判断不算完成。
  - 失效方式：把术语当标签，却没有改变产品行为或验证方法。

## 关键概念

- **Challenge / 挑战**：在效率、透明度、安全、文化和组织利益冲突下持续管理复杂性。
- **Service System / 服务系统**：由人、渠道、规则、后台流程与触点共同完成结果的整体。
- **Necessary Complexity / 必要复杂性**：复杂任务本身具有不可消除的结构；目标是使其可理解和可管理，而不是假装不存在。

## 心智模型

- 把本章看成一个决策过滤器：把政策、所有权、激励和跨团队依赖纳入问题模型，设置端到端结果指标。
- 当局部界面“看起来合理”却让人迟疑时，回到用户目标、情境和反馈链，而不是继续装饰表面。
- 设计主张必须能被研究证据、行为结果或可用性观察推翻；不能被推翻的主张只是偏好。

## 反模式

- **把治理问题界面化**：把组织性失败留给用户用耐心和记忆补偿。
- **术语替代证据**：引用框架名称却没有说明用户、任务、约束和验证信号，会让团队产生虚假的确定性。

## Worked Example

医院预约系统的重复填写可能源于部门数据不互通；真正修复需要身份、权限和责任协议，而不只是自动填表。

把例子重新应用到自己的产品时，保留同样的推理顺序：先写目标与情境，再写设计动作，最后写可观察的成功/失败信号。

## 关键结论

1. 把政策、所有权、激励和跨团队依赖纳入问题模型，设置端到端结果指标。
2. 把“Challenge / 挑战”落实为可观察的界面或流程行为，而不是停留在口号。
3. 用真实情境检查“Necessary Complexity / 必要复杂性”，并记录失败条件。
