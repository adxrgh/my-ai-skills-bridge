# 第 8 章：管理复杂：设计师和使用者的伙伴关系

## 核心思想

管理复杂需要让人和系统各做擅长的事，并允许人在例外中接管。

## 本章框架

- **Partnership / 人机伙伴关系**：人负责目标、价值与例外判断，系统负责计算、记忆和稳定执行的互补分工。
  - 何时使用：当自动化既不能完全可靠、又可能让人失去情境意识时。
  - 如何使用：分配目标、感知、计算、执行与监督责任；为边界情况提供解释、撤销和升级。
  - 失效方式：自动化常态任务后，却要求人瞬间处理从未见过的异常。
- **Coping / 应对机制**：人在复杂系统中借助惯例、外部记忆、分工和近似规则维持行动。
  - 何时使用：当“管理复杂：设计师和使用者的伙伴关系”相关决策存在多个看似合理的选项时。
  - 如何使用：先标出用户目标与约束，再用“Coping / 应对机制”逐项检查方案；无法观察或验证的判断不算完成。
  - 失效方式：把术语当标签，却没有改变产品行为或验证方法。
- **Necessary Complexity / 必要复杂性**：复杂任务本身具有不可消除的结构；目标是使其可理解和可管理，而不是假装不存在。
  - 何时使用：当“管理复杂：设计师和使用者的伙伴关系”相关决策存在多个看似合理的选项时。
  - 如何使用：先标出用户目标与约束，再用“Necessary Complexity / 必要复杂性”逐项检查方案；无法观察或验证的判断不算完成。
  - 失效方式：把术语当标签，却没有改变产品行为或验证方法。

## 关键概念

- **Partnership / 人机伙伴关系**：人负责目标、价值与例外判断，系统负责计算、记忆和稳定执行的互补分工。
- **Coping / 应对机制**：人在复杂系统中借助惯例、外部记忆、分工和近似规则维持行动。
- **Necessary Complexity / 必要复杂性**：复杂任务本身具有不可消除的结构；目标是使其可理解和可管理，而不是假装不存在。

## 心智模型

- 把本章看成一个决策过滤器：分配目标、感知、计算、执行与监督责任；为边界情况提供解释、撤销和升级。
- 当局部界面“看起来合理”却让人迟疑时，回到用户目标、情境和反馈链，而不是继续装饰表面。
- 设计主张必须能被研究证据、行为结果或可用性观察推翻；不能被推翻的主张只是偏好。

## 反模式

- **自动化悖论**：自动化常态任务后，却要求人瞬间处理从未见过的异常。
- **术语替代证据**：引用框架名称却没有说明用户、任务、约束和验证信号，会让团队产生虚假的确定性。

## Worked Example

驾驶辅助负责稳定车道，人保留路线与风险判断；系统必须持续表达置信度和边界，接管请求要留出真实反应时间。

把例子重新应用到自己的产品时，保留同样的推理顺序：先写目标与情境，再写设计动作，最后写可观察的成功/失败信号。

## 关键结论

1. 分配目标、感知、计算、执行与监督责任；为边界情况提供解释、撤销和升级。
2. 把“Partnership / 人机伙伴关系”落实为可观察的界面或流程行为，而不是停留在口号。
3. 用真实情境检查“Necessary Complexity / 必要复杂性”，并记录失败条件。
