# 方法与模式 — 设计心理学2：如何管理复杂

## Necessary Complexity / 必要复杂性

**何时使用**：当“更简单”成为没有目标和代价说明的需求时。

**如何使用**：先分离任务固有复杂性与设计制造的费解感，再决定哪些结构必须保留、哪些负担可以转移。

**权衡**：把功能数量直接当作复杂度指标，忽略关系和概念模型。

**来源**：Ch 1「设计复杂生活：为什么复杂是必需的」

## Conceptual Simplicity / 概念简单

**何时使用**：当团队用视觉极简推断认知简单时。

**如何使用**：测试用户能否形成稳定预测，而不仅是首次看到的整洁程度。

**权衡**：把控件隐藏进模式和菜单，造成记忆与恢复成本。

**来源**：Ch 2「简单只存在于头脑中」

## False Simplicity / 虚假简单

**何时使用**：当某个团队宣布步骤减少，但投诉、等待或人工处理增加时。

**如何使用**：沿端到端旅程绘制复杂性转移：谁在何时承担记忆、协调、异常和恢复。

**权衡**：只优化自己的屏幕或部门指标。

**来源**：Ch 3「简单的东西如何使生活更复杂」

## Social Signifiers / 社会性意符

**何时使用**：当空间或协作产品缺少明确规则但存在群体行为时。

**如何使用**：识别队列、磨损痕迹、已读状态等社会线索，保留有用信号并防止误导。

**权衡**：把所有行为线索清理掉，迫使每个人重新探索。

**来源**：Ch 4「社会性语义符号」

## Sociable Design / 善于交际的设计

**何时使用**：当自动化在没有解释或许可时打断、替用户行动时。

**如何使用**：检查时机、语气、授权、可见状态和退出方式；让系统的“社交动作”符合关系。

**权衡**：用拟人文案掩盖强制行为和信息不对称。

**来源**：Ch 5「善于交际的设计」

## Service System / 服务系统

**何时使用**：当问题跨 App、客服、物流、门店或政策边界时。

**如何使用**：画出前台触点、后台流程、责任和信息交接，围绕用户结果而非部门组织改造。

**权衡**：只重做界面，不改变造成失败的规则与交接。

**来源**：Ch 6「系统和服务」

## Designing Waiting / 等待设计

**何时使用**：当过程不可即时完成或时间波动很大时。

**如何使用**：先给可信预期和原因，再展示有意义进度、保留选择，并及时更新变化。

**权衡**：用虚假进度条或乐观时间制造二次失望。

**来源**：Ch 7「对等待的设计」

## Partnership / 人机伙伴关系

**何时使用**：当自动化既不能完全可靠、又可能让人失去情境意识时。

**如何使用**：分配目标、感知、计算、执行与监督责任；为边界情况提供解释、撤销和升级。

**权衡**：自动化常态任务后，却要求人瞬间处理从未见过的异常。

**来源**：Ch 8「管理复杂：设计师和使用者的伙伴关系」

## Challenge / 挑战

**何时使用**：当明确的界面修复在组织内反复失败时。

**如何使用**：把政策、所有权、激励和跨团队依赖纳入问题模型，设置端到端结果指标。

**权衡**：把组织性失败留给用户用耐心和记忆补偿。

**来源**：Ch 9「挑战」
