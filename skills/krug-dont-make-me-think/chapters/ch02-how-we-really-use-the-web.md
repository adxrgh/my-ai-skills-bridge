# 第 2 章：How We Really Use the Web

## 核心思想

人们通常快速扫描、猜测并勉强前进，而不是认真阅读和理性比较。

## 本章框架

- **Satisficing / 满意即止**：用户通常扫描并选择第一个看起来足够可行的选项，而非优化所有选择。
  - 何时使用：当设计评审假设用户会按顺序阅读所有内容时。
  - 如何使用：让关键词、标题和可点击目标支持扫描；重要路径不能依赖完整阅读。
  - 失效方式：用理想化“细心用户”解释测试失败。
- **Scanning / 扫描**：人按标题、关键词、形状和视觉层级快速寻找相关区域，而非逐字阅读。
  - 何时使用：当“How We Really Use the Web”相关决策存在多个看似合理的选项时。
  - 如何使用：先标出用户目标与约束，再用“Scanning / 扫描”逐项检查方案；无法观察或验证的判断不算完成。
  - 失效方式：把术语当标签，却没有改变产品行为或验证方法。
- **Conventions / 约定**：复用人已学会的界面模式，减少解释成本。
  - 何时使用：当“How We Really Use the Web”相关决策存在多个看似合理的选项时。
  - 如何使用：先标出用户目标与约束，再用“Conventions / 约定”逐项检查方案；无法观察或验证的判断不算完成。
  - 失效方式：把术语当标签，却没有改变产品行为或验证方法。

## 关键概念

- **Satisficing / 满意即止**：用户通常扫描并选择第一个看起来足够可行的选项，而非优化所有选择。
- **Scanning / 扫描**：人按标题、关键词、形状和视觉层级快速寻找相关区域，而非逐字阅读。
- **Conventions / 约定**：复用人已学会的界面模式，减少解释成本。

## 心智模型

- 把本章看成一个决策过滤器：让关键词、标题和可点击目标支持扫描；重要路径不能依赖完整阅读。
- 当局部界面“看起来合理”却让人迟疑时，回到用户目标、情境和反馈链，而不是继续装饰表面。
- 设计主张必须能被研究证据、行为结果或可用性观察推翻；不能被推翻的主张只是偏好。

## 反模式

- **逐字阅读假设**：用理想化“细心用户”解释测试失败。
- **术语替代证据**：引用框架名称却没有说明用户、任务、约束和验证信号，会让团队产生虚假的确定性。

## Worked Example

测试者在新闻页只看标题和粗体词，点第一个像答案的链接；设计应让该扫描路径仍能通向正确结果。

把例子重新应用到自己的产品时，保留同样的推理顺序：先写目标与情境，再写设计动作，最后写可观察的成功/失败信号。

## 关键结论

1. 让关键词、标题和可点击目标支持扫描；重要路径不能依赖完整阅读。
2. 把“Satisficing / 满意即止”落实为可观察的界面或流程行为，而不是停留在口号。
3. 用真实情境检查“Conventions / 约定”，并记录失败条件。
