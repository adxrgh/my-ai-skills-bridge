# 第 4 章：机器的仆人

## 核心思想

技术若把配置、监控和异常处理转嫁给人，人就成为机器的维护者。

## 本章框架

- **Machine Servitude / 机器的仆人**：人被迫监控、喂数据、维护和迁就自动化，反而为机器劳动。
  - 何时使用：当自动化节省的时间被设置、纠错和数据整理抵消时。
  - 如何使用：计算完整拥有成本：配置、监督、异常、更新、迁移和退出，而不只算正常流。
  - 失效方式：宣传自动化率，却忽略人类隐形劳动。
- **Automation / 自动化**：让机器在一定授权和条件下感知、判断或行动；其边界必须可理解。
  - 何时使用：当“机器的仆人”相关决策存在多个看似合理的选项时。
  - 如何使用：先标出用户目标与约束，再用“Automation / 自动化”逐项检查方案；无法观察或验证的判断不算完成。
  - 失效方式：把术语当标签，却没有改变产品行为或验证方法。
- **Graceful Degradation / 优雅降级**：能力或信息不足时安全地降低功能，并保持核心控制与恢复。
  - 何时使用：当“机器的仆人”相关决策存在多个看似合理的选项时。
  - 如何使用：先标出用户目标与约束，再用“Graceful Degradation / 优雅降级”逐项检查方案；无法观察或验证的判断不算完成。
  - 失效方式：把术语当标签，却没有改变产品行为或验证方法。

## 关键概念

- **Machine Servitude / 机器的仆人**：人被迫监控、喂数据、维护和迁就自动化，反而为机器劳动。
- **Automation / 自动化**：让机器在一定授权和条件下感知、判断或行动；其边界必须可理解。
- **Graceful Degradation / 优雅降级**：能力或信息不足时安全地降低功能，并保持核心控制与恢复。

## 心智模型

- 把本章看成一个决策过滤器：计算完整拥有成本：配置、监督、异常、更新、迁移和退出，而不只算正常流。
- 当局部界面“看起来合理”却让人迟疑时，回到用户目标、情境和反馈链，而不是继续装饰表面。
- 设计主张必须能被研究证据、行为结果或可用性观察推翻；不能被推翻的主张只是偏好。

## 反模式

- **自动化账面收益**：宣传自动化率，却忽略人类隐形劳动。
- **术语替代证据**：引用框架名称却没有说明用户、任务、约束和验证信号，会让团队产生虚假的确定性。

## Worked Example

智能家居若每次换路由器都需重配所有设备，实际负担高。应提供本地身份、批量迁移、离线核心功能和清晰故障定位。

把例子重新应用到自己的产品时，保留同样的推理顺序：先写目标与情境，再写设计动作，最后写可观察的成功/失败信号。

## 关键结论

1. 计算完整拥有成本：配置、监督、异常、更新、迁移和退出，而不只算正常流。
2. 把“Machine Servitude / 机器的仆人”落实为可观察的界面或流程行为，而不是停留在口号。
3. 用真实情境检查“Graceful Degradation / 优雅降级”，并记录失败条件。
