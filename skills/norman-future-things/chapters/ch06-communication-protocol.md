# 第 6 章：与机器沟通

## 核心思想

协作需要持续建立共同基础：双方知道目标、状态、意图和理解差异。

## 本章框架

- **Communication Protocol / 沟通协议**：系统表达意图、状态、不确定性以及请求接管的稳定方式。
  - 何时使用：当系统行动跨时间、后台执行或依赖不完整信息时。
  - 如何使用：用稳定信号表达计划、进度、阻塞、不确定性与需要用户决定的节点。
  - 失效方式：把所有沟通压缩成成功或失败两个终态。
- **Common Ground / 共同基础**：协作者对目标、状态、意图和知识范围拥有足够共享理解。
  - 何时使用：当“与机器沟通”相关决策存在多个看似合理的选项时。
  - 如何使用：先标出用户目标与约束，再用“Common Ground / 共同基础”逐项检查方案；无法观察或验证的判断不算完成。
  - 失效方式：把术语当标签，却没有改变产品行为或验证方法。
- **Automation Surprise / 自动化惊奇**：系统行为与人的预期不一致，通常源于隐藏模式、目标或信息不对称。
  - 何时使用：当“与机器沟通”相关决策存在多个看似合理的选项时。
  - 如何使用：先标出用户目标与约束，再用“Automation Surprise / 自动化惊奇”逐项检查方案；无法观察或验证的判断不算完成。
  - 失效方式：把术语当标签，却没有改变产品行为或验证方法。

## 关键概念

- **Communication Protocol / 沟通协议**：系统表达意图、状态、不确定性以及请求接管的稳定方式。
- **Common Ground / 共同基础**：协作者对目标、状态、意图和知识范围拥有足够共享理解。
- **Automation Surprise / 自动化惊奇**：系统行为与人的预期不一致，通常源于隐藏模式、目标或信息不对称。

## 心智模型

- 把本章看成一个决策过滤器：用稳定信号表达计划、进度、阻塞、不确定性与需要用户决定的节点。
- 当局部界面“看起来合理”却让人迟疑时，回到用户目标、情境和反馈链，而不是继续装饰表面。
- 设计主张必须能被研究证据、行为结果或可用性观察推翻；不能被推翻的主张只是偏好。

## 反模式

- **沉默的自动化**：把所有沟通压缩成成功或失败两个终态。
- **术语替代证据**：引用框架名称却没有说明用户、任务、约束和验证信号，会让团队产生虚假的确定性。

## Worked Example

旅行代理改签前应说明发现的冲突、候选方案、费用和授权边界；执行后保留可追溯记录与撤销路径。

把例子重新应用到自己的产品时，保留同样的推理顺序：先写目标与情境，再写设计动作，最后写可观察的成功/失败信号。

## 关键结论

1. 用稳定信号表达计划、进度、阻塞、不确定性与需要用户决定的节点。
2. 把“Communication Protocol / 沟通协议”落实为可观察的界面或流程行为，而不是停留在口号。
3. 用真实情境检查“Automation Surprise / 自动化惊奇”，并记录失败条件。
