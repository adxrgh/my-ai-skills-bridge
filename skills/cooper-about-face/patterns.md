# 方法与模式 — About Face 4：交互设计精髓

## Goal-Directed Design / 目标导向设计

**何时使用**：当需求主要由市场清单和技术能力组成时。

**如何使用**：按研究、建模、需求、框架、提炼和支持阶段推进，每个设计决定回链到人物目标。

**权衡**：让开发过程自然“长出”交互，或把设计降为视觉装饰。

**来源**：Ch 1「数字产品的设计过程」

## Design Research / 设计研究

**何时使用**：当团队只拥有调查百分比、需求票据或内部意见时。

**如何使用**：先访谈利益相关者和领域专家，再在真实情境观察代表用户；记录行为、目标、环境和例外。

**权衡**：只问用户想要哪些功能，或让焦点小组投票设计。

**来源**：Ch 2「理解问题：设计研究」

## Persona / 人物模型

**何时使用**：当团队以“所有用户”或随讨论变化的弹性用户做决定时。

**如何使用**：按行为变量聚类，综合人物模型和目标，检查完整与冗余，再指定首要、次要等类型。

**权衡**：用人口统计画像、虚构故事或平均用户替代研究模式。

**来源**：Ch 3「为用户建模：人物模型和目标」

## Scenario / 场景

**何时使用**：当研究资料丰富但团队直接跳到线框图时。

**如何使用**：写问题与愿景，构建情境场景，逐句提取对象、动作、信息和约束，形成需求。

**权衡**：把用户故事或功能规格当成完整场景。

**来源**：Ch 4「设立愿景：场景和设计需求」

## Interaction Framework / 交互框架

**何时使用**：当团队有大量页面草图却没有稳定产品模型时。

**如何使用**：定义外形与姿态、功能和数据分组、层级与关键路径；验证后再细化状态、术语和视觉。

**权衡**：一开始就高保真，导致团队围绕颜色而非行为争论。

**来源**：Ch 5「设计产品：框架和提炼」

## Design Collaboration / 设计协作

**何时使用**：当设计被拆成互不相连的交付件或只由会议协商产生时。

**如何使用**：保持核心团队共同工作，让设计、开发和业务围绕同一人物目标及框架频繁校准。

**权衡**：设计委员会用妥协拼接每个人偏好。

**来源**：Ch 6「创造型团队合作」

## Design Principle / 设计原则

**何时使用**：当团队反复解决相似问题或标准不一致时。

**如何使用**：记录问题、适用情境、解决结构和权衡；评审时说明原则如何服务当前目标。

**权衡**：把模式库当控件目录或把原则当绝对规则。

**来源**：Ch 7「良好产品行为的基础」

## Digital Etiquette / 数字产品礼仪

**何时使用**：当产品反复询问、责怪、忘记或替用户做主时。

**如何使用**：检查产品是否记住已知信息、预见常见需要、解释状态、承担错误并尊重隐私。

**权衡**：用友好文案包装同样粗鲁的行为。

**来源**：Ch 8「数字产品的礼仪」

## Posture / 姿态

**何时使用**：当同一界面被机械搬到桌面、Web、手机或信息亭时。

**如何使用**：先判断独占、暂时、后台等姿态，再结合平台约定决定结构和行为。

**权衡**：把响应式尺寸变化误当跨平台设计。

**来源**：Ch 9「平台和姿态」

## Perpetual Intermediate / 永久的中级用户

**何时使用**：当界面在新手向导与专家快捷键之间断层时。

**如何使用**：默认呈现高频工作集，提供可发现的高级路径和加速方式，避免永久训练轮。

**权衡**：长期为新手简化，迫使熟练用户重复低效步骤。

**来源**：Ch 10「为中级用户优化设计」

## Orchestration and Flow / 编配与流

**何时使用**：当流程充满模态框、页面跳转和状态丢失时。

**如何使用**：按心理模型组织对象与动作，提供选择而非审问，用非模态反馈维持上下文。

**权衡**：每一步都要求确认或切换页面。

**来源**：Ch 11「编配与流」

## Eliminate Excise / 消除负担

**何时使用**：当完成简单目标需要多次搬运、定位或确认时。

**如何使用**：把每一步标为目标任务或负担；通过记忆、默认、合并、直接入口和更好映射消除负担。

**权衡**：只减少点击数，却增加判断和错误风险。

**来源**：Ch 12「减少工作，消除负担」

## Affordance and Idiom / 能供性与习惯用法

**何时使用**：当团队为“直观”强行模拟现实物体时。

**如何使用**：区分真实能供性、已学会的习惯用法和装饰隐喻；选择最能支持目标与反馈的方式。

**权衡**：隐喻限制数字能力，或把任何拖拽都叫自然。

**来源**：Ch 13「隐喻、习惯用法及能供性」

## Unified File Model / 统一文件模型

**何时使用**：当用户频繁管理保存、版本、路径和格式时。

**如何使用**：自动保存、保留版本、按内容与关系检索，并让导出成为明确的共享动作。

**权衡**：隐藏存储状态或锁死数据，造成新的不透明。

**来源**：Ch 14「重新思考数据输入、存储与检索」

## Error Prevention / 防错

**何时使用**：当产品用大量错误框和“你确定吗”保障安全时。

**如何使用**：约束无效动作、提供预览和撤销、持续显示影响；只有高风险不可逆节点才确认。

**权衡**：确认疲劳让人机械点击。

**来源**：Ch 15「防止错误、通知决定」

## Learnability / 易学性

**何时使用**：当产品准备本地化、定制、帮助或无障碍适配时。

**如何使用**：把差异纳入人物模型与框架，保持核心一致，允许适度配置并提供上下文帮助。

**权衡**：无限定制把设计责任转给用户。

**来源**：Ch 16「为不同的需求而设计」

## Visual Hierarchy / 视觉层级

**何时使用**：当视觉稿漂亮但任务层级与状态不清时。

**如何使用**：用形状、大小、位置、颜色、文字和动效表达优先级、分组、因果与状态，并控制视觉工作量。

**权衡**：品牌装饰覆盖行为层级或仅靠颜色传达。

**来源**：Ch 17「整合视觉设计」

## Desktop Posture / 桌面姿态

**何时使用**：当设计生产力或专业桌面工具时。

**如何使用**：围绕主窗口和工作对象组织命令，支持选择、拖放、键盘和多窗口状态，遵守平台约定。

**权衡**：用网页卡片模式取代高效桌面工作流。

**来源**：Ch 18「为桌面应用而设计」

## Mobile Posture / 移动姿态

**何时使用**：当功能进入手机、平板、信息亭、汽车或语音设备时。

**如何使用**：识别核心情境与输入方式，保证目标尺寸、反馈、单手与无障碍，并尊重平台习惯。

**权衡**：把桌面控件缩小或创造无提示手势。

**来源**：Ch 19「为移动设备和其他设备而设计」

## Web Interaction / Web 交互

**何时使用**：当设计内容网站或 Web 应用的信息架构与流程时。

**如何使用**：保持位置与导航可见，链接行为一致，长流程保存状态，并分别处理页面浏览与应用工作。

**权衡**：在应用中模拟网站跳转，或在网站中隐藏浏览路径。

**来源**：Ch 20「网页的设计」

## Controls / 控件

**何时使用**：当细化表单、设置、列表和高风险操作时。

**如何使用**：按数据类型、选项数量、频率和风险选择控件；保持标签、默认、状态、验证与键盘行为一致。

**权衡**：为每个动作发明新控件，或用模态框承载常规流程。

**来源**：Ch 21「设计细节：控件和对话框」
