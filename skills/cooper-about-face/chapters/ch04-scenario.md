# 第 4 章：设立愿景：场景和设计需求

## 核心思想

场景把人物目标转成未来行为叙事，需求描述交互必须提供什么，而非提前指定控件。

## 本章框架

- **Scenario / 场景**：以人物模型为主角、围绕目标描述未来使用情境的叙事工具。
  - 何时使用：当研究资料丰富但团队直接跳到线框图时。
  - 如何使用：写问题与愿景，构建情境场景，逐句提取对象、动作、信息和约束，形成需求。
  - 失效方式：把用户故事或功能规格当成完整场景。
- **Requirements Definition / 需求定义**：从问题、人物模型、场景和约束推导产品必须提供的能力、信息与情境。
  - 何时使用：当“设立愿景：场景和设计需求”相关决策存在多个看似合理的选项时。
  - 如何使用：先标出用户目标与约束，再用“Requirements Definition / 需求定义”逐项检查方案；无法观察或验证的判断不算完成。
  - 失效方式：把术语当标签，却没有改变产品行为或验证方法。
- **Persona / 人物模型**：由研究模式综合出的具体行为原型，用来聚焦设计和避免弹性用户。
  - 何时使用：当“设立愿景：场景和设计需求”相关决策存在多个看似合理的选项时。
  - 如何使用：先标出用户目标与约束，再用“Persona / 人物模型”逐项检查方案；无法观察或验证的判断不算完成。
  - 失效方式：把术语当标签，却没有改变产品行为或验证方法。

## 关键概念

- **Scenario / 场景**：以人物模型为主角、围绕目标描述未来使用情境的叙事工具。
- **Requirements Definition / 需求定义**：从问题、人物模型、场景和约束推导产品必须提供的能力、信息与情境。
- **Persona / 人物模型**：由研究模式综合出的具体行为原型，用来聚焦设计和避免弹性用户。

## 心智模型

- 把本章看成一个决策过滤器：写问题与愿景，构建情境场景，逐句提取对象、动作、信息和约束，形成需求。
- 当局部界面“看起来合理”却让人迟疑时，回到用户目标、情境和反馈链，而不是继续装饰表面。
- 设计主张必须能被研究证据、行为结果或可用性观察推翻；不能被推翻的主张只是偏好。

## 反模式

- **控件先行**：把用户故事或功能规格当成完整场景。
- **术语替代证据**：引用框架名称却没有说明用户、任务、约束和验证信号，会让团队产生虚假的确定性。

## Worked Example

为外勤维修员写从接单到离线记录再到同步的情境场景，由此推导状态、地图、证据采集和冲突处理需求。

把例子重新应用到自己的产品时，保留同样的推理顺序：先写目标与情境，再写设计动作，最后写可观察的成功/失败信号。

## 关键结论

1. 写问题与愿景，构建情境场景，逐句提取对象、动作、信息和约束，形成需求。
2. 把“Scenario / 场景”落实为可观察的界面或流程行为，而不是停留在口号。
3. 用真实情境检查“Persona / 人物模型”，并记录失败条件。
