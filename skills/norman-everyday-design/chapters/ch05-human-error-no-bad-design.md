# 第 5 章：人为差错？不，是拙劣设计 / Human Error? No, Bad Design

## 核心思想

把“人为错误”当终点会掩盖系统诱因；设计应防错、容错并支持恢复。

## 本章框架

- **Slips and Mistakes / 失误与错误**：失误是执行偏离意图，错误是目标或计划本身不合适；两者需要不同修复。
  - 何时使用：当事故报告以“用户没有注意”或“未遵守流程”结束时。
  - 如何使用：先区分失误与错误，再用根因分析追查目标、信息、模式、时间压力、反馈和组织条件；优先改变系统。
  - 失效方式：增加培训、警告和责任追究，却保留同样的诱错结构。
- **Root Cause Analysis / 根因分析**：越过操作者表面行为，追查导致失败的系统条件和设计决策。
  - 何时使用：当“人为差错？不，是拙劣设计 / Human Error? No, Bad Design”相关决策存在多个看似合理的选项时。
  - 如何使用：先标出用户目标与约束，再用“Root Cause Analysis / 根因分析”逐项检查方案；无法观察或验证的判断不算完成。
  - 失效方式：把术语当标签，却没有改变产品行为或验证方法。
- **Constraints / 约束**：通过物理、文化、语义或逻辑关系限制不合适的行动。
  - 何时使用：当“人为差错？不，是拙劣设计 / Human Error? No, Bad Design”相关决策存在多个看似合理的选项时。
  - 如何使用：先标出用户目标与约束，再用“Constraints / 约束”逐项检查方案；无法观察或验证的判断不算完成。
  - 失效方式：把术语当标签，却没有改变产品行为或验证方法。
- **Feedback / 反馈**：及时、可解释地呈现行动已发生以及系统变成了什么状态。
  - 何时使用：当“人为差错？不，是拙劣设计 / Human Error? No, Bad Design”相关决策存在多个看似合理的选项时。
  - 如何使用：先标出用户目标与约束，再用“Feedback / 反馈”逐项检查方案；无法观察或验证的判断不算完成。
  - 失效方式：把术语当标签，却没有改变产品行为或验证方法。

## 关键概念

- **Slips and Mistakes / 失误与错误**：失误是执行偏离意图，错误是目标或计划本身不合适；两者需要不同修复。
- **Root Cause Analysis / 根因分析**：越过操作者表面行为，追查导致失败的系统条件和设计决策。
- **Constraints / 约束**：通过物理、文化、语义或逻辑关系限制不合适的行动。
- **Feedback / 反馈**：及时、可解释地呈现行动已发生以及系统变成了什么状态。

## 心智模型

- 把本章看成一个决策过滤器：先区分失误与错误，再用根因分析追查目标、信息、模式、时间压力、反馈和组织条件；优先改变系统。
- 当局部界面“看起来合理”却让人迟疑时，回到用户目标、情境和反馈链，而不是继续装饰表面。
- 设计主张必须能被研究证据、行为结果或可用性观察推翻；不能被推翻的主张只是偏好。

## 反模式

- **把人当作故障部件**：增加培训、警告和责任追究，却保留同样的诱错结构。
- **术语替代证据**：引用框架名称却没有说明用户、任务、约束和验证信号，会让团队产生虚假的确定性。

## Worked Example

有人把相邻且外形相同的两个开关拨错。与其贴“请小心”标签，不如把开关按设备空间位置重新映射、增加形状区分，并提供可逆操作和明显状态反馈。

把例子重新应用到自己的产品时，保留同样的推理顺序：先写目标与情境，再写设计动作，最后写可观察的成功/失败信号。

## 关键结论

1. 先区分失误与错误，再用根因分析追查目标、信息、模式、时间压力、反馈和组织条件；优先改变系统。
2. 把“Slips and Mistakes / 失误与错误”落实为可观察的界面或流程行为，而不是停留在口号。
3. 用真实情境检查“Feedback / 反馈”，并记录失败条件。
